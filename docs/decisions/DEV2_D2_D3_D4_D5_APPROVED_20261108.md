## D2 — DEC-DEV2-D2-001 (approved)

**CSV is an emergency/fallback import** to read source data only; it cannot write CFO plans/approvals.

1. **Encoding/schema:** UTF-8 with optional BOM; RFC 4180 quoting, comma delimiter, one header row and explicitly versioned schema, consistent with Source API entity fields. Decimal uses a dot, no thousands separator; money exact two-place decimal strings; local dates ISO `YYYY-MM-DD`; timestamps ISO 8601 with offset, converted to UTC for storage. Unknown schema version, unknown headers/market and invalid number/date are rejected with per-row/type error records.
2. **Relationships:** represent order and order lines as `orders.csv` and `order_lines.csv` with `order_id` key; no arbitrary JSON blobs in a CSV cell. Market/entity/source snapshot metadata in upload manifest, including authoritative `captured_at` and file SHA-256. Stock import requires a coherent **complete snapshot batch** with explicit empty-batch completeness; never sum source alias rows indiscriminately (D1 SRC-Q9/Q10 remain to be fully specified).
3. **Duplicate/retry:** file SHA-256 scoped to market+entity+schema_version. Same hash with previous `ok` => skip idempotently; `failed` => new recorded retry; `partial` => requires IT review/retry, not silently treated as success; currently `running` => 409. Each retry preserves the original run history; unique index/migration must accommodate retries. Idempotent row upsert by natural key and source version, reject conflicting duplicate keys; do not double-count stock and do not advance sync checkpoint after an incomplete run.
4. **Privacy/permissions:** IT/admin-only operation, non-PII technical rejection logs, no source-to-CFO writeback; audit uploads and outcomes.
5. **Test:** malformed UTF-8/headers/dates, duplicate valid file, failed retry, partial manual retry, overlapping workers, line referential integrity, stock alias collisions, rollback and idempotency.

## D3 — DEC-DEV2-D3-001 (approved policy, DTO implementation details need contract tests)

**GPS applies to a driver *only* while a specifically assigned delivery trip is actually `on_road` AND the driver is in the verified official work shift, the market has `gps_enabled=true`, and the driver has been informed of the tracking purpose. It is NOT an employee work-hour tracking system.** Approved collection frequency: **every 30 minutes**. No collection before departure, outside driver shift, after cancellation/completion, or in the gap until next trip is `on_road`. A new trip starts a new, separately authorized GPS session; no continuing background tracking.

1. **Driver write:** `POST /trips/{trip_id}/positions` authenticates driver via JWT and derives `employee_id` from trusted server-side assignment; never trust an arbitrary client-supplied `driver_id`. Accepted point: `lat`, `lon`, `recorded_at` with timezone, `accuracy_m?`, and `source=device|simulator`; only privacy-necessary device metadata, **no unrestricted hardware fingerprint/device ID**. Suggest bounded upload 1–100 points/batch, per-trip replay/idempotency key and bounded lookback while trip remains active. Coordinates validate lat [-90,90], lon [-180,180], accuracy >0; timestamps must belong to authorized trip and official shift.
2. **Offline queue approved:** store encrypted/private local pending points only until trip ends / driver's official shift ends, whichever first. On reconnect, upload only points whose original timestamp belongs to that active trip and verified shift and while server still reports `on_road`; server revalidates access and rejects late points after terminal status. If a trip ends offline, clear queued points on client at next app activation/sync and reject them server-side (no backfill into completed trips). Do not silently continue location capture outside shift. Browser/PWA background GPS cannot be promised when OS/browser suspends.
3. **Dispatcher read:** `GET /gps/live` and `GET /trips/{id}/positions` limited to **trips explicitly assigned to that Dispatcher** and **the driver's valid work period**, and only while trip is active and on road. Other Dispatcher accounts, even in the same market, must not view GPS. No historical GPS read after trip completion/cancellation/shift end. Driver may get own upload acknowledgements/status only; not GPS of other drivers. CS, sales, warehouse, admin, customer, viewer never get coordinates. Backend requires durable authorized **dispatcher-to-trip assignment/scope**: if missing, fail closed, no fallback to entire market; Dev 1 must review contract/migration if current data model lacks this mapping. Access must be checked on every request, not just in UI.
4. **Retention override:** **raw GPS persists only during active delivery trip and verified duty interval. As soon as trip reaches terminal `completed`/`cancelled` or driver exits verified duty, immediately stop collection and purge raw coordinates for that tracking session**; no "30 days after trip" rule. For multiple stops/orders in one trip, use trip termination (last stop and return as modeled), not early completion of first stop. Purge in the same completion workflow where feasible, plus idempotent privacy cleanup for crash/retry; zero raw GPS points should remain in application DB or offline queue after cleanup. Retain only non-coordinate operational milestones and separately regulated duty/tachograph/working-time evidence under D5 (do NOT mistake it for live GPS). Backup/delete propagation must be assessed and reported: do not claim physical immediate erasure from preexisting immutable provider backups.
5. **Settings:** interval `interval_min=30` (no unapproved automatic higher-frequency sampling), lost threshold proposed `lost_min=60` consistent with current config, retention mode `trip_end_delete` (new contract semantic; existing `retention_days=30` must be superseded, not silently left active), `gps_enabled`, and explicit privacy-warning/DPIA state. Treat configurable numeric limits and response envelope as Dev 2 contract work requiring Dev 1/Dev 3 review, **not extra owner approvals**.
6. **Loss/ETA:** if no point for 60 minutes during active authorized trip+shift, raise `GPS_LOST`, do not infer tracking when driver is off duty, do not auto-restart GPS. ETA uses last valid fresh point or falls back to non-GPS route/milestones after signal loss, labeled as estimate. Alerts contain no coordinates or personnel details.
7. **Test:** wrong-driver write, wrong-Dispatcher read, cross-market access, off-shift read/write, pre-departure/post-termination write, repeated offline replay, completion while offline, multiple stops/trips, concurrent completion vs uploaded batch, deletion on cancelled/failed terminal, DB restore/backups, privacy logs, and 30-min frequency.
8. **GDPR:** Swedish IMY guidance states private employers must assess legitimate interest and normally must not track vehicle positions outside working hours nor repurpose GPS to monitor rest/working hours. For real GPS, legal/privacy review and DPIA where applicable before release: https://www.imy.se/verksamhet/dataskydd/dataskydd-pa-olika-omraden/arbetsliv/kontroll-och-overvakning-av-anstallda/

## D4 — DEC-DEV2-D4-001 (approved)

1. Customer notifications use **server-rendered allowlisted templates** `CONFIRMED`, `DISPATCHED`, `DELIVERED`, `FAILED`, `DELAY`. Templates are versioned and locale-aware. **No arbitrary free-text email/SMS body or subject** from Dispatcher, source POS or API. Only allowlisted variables from verified order/public reference, approved status, approved delivery window/ETA, and reviewed standard service notice. Driver name, GPS/coordinates, internal risk values, private staff/store data, arbitrary CS notes or user-submitted text cannot become template variables.
2. `DELAY` remains **Dispatcher-approved draft**: Dispatcher can update the validated `eta_window`, choose a reviewed `reason_code`/phrase from enum, preview the server-generated message and explicitly Send or Discard (discard requires reason). Other four templates remain triggered by workflow. `POST /orders/{id}/delay-notice` creates a draft only; it must NOT circumvent dispatcher authorization.
3. `POST /notifications/{id}/send` should accept `eta_window`, approved reason/template-variable choices and `Idempotency-Key`; reject arbitrary `body` or non-allowlisted variable at 422; renderer ignores raw source free text. If legacy `body` field exists, it may be accepted only when it exactly matches the server-generated canonical preview, without granting editing permissions; cleaner contract is to remove it in a reviewed versioned API.
4. Existing quiet-hours policy `21:00–07:00` market-local with controlled Dispatcher-triggered DELAY exception and existing max-attempts cap 3 remain. The previous technical proposal of **retry after 5min then 15min** needs an explicit approved contract/implementation review; owner approval of templates alone does not silently approve a new retry schedule. No real-customer email until DEC-NOTIFY-001's dedupe/reconciliation issue is solved; use Mailpit/staging allowlist.
5. Test template injection/unknown variable, wrong-role DELAY, preview/send parity, retry idempotency, timezone and quiet hours, no GPS/PII in text/email/logs.

## D5 — DEC-DEV2-D5-001 (approved policy for synthetic MVP; real-data legal gate remains)

Owner approved the numerical GDPR-aware retention **recommendations** from [PR #87](https://github.com/qaztyhn/cfo-itconsultant/pull/87), **subject to D3 override that raw GPS is deleted on trip termination, not 30 days later**. GDPR itself does not impose these arbitrary calendar-day defaults. `DEC-GDPR-001` GDPR-by-design objective is also owner approved; its unmerged earlier documentation PR #86 should be reconciled rather than silently merged twice.

| Category | Owner-approved policy for CFO pilot | Anchor / limits |
|---|---|---|
| Raw GPS coordinates on server/driver PWA | **Immediate purge at trip terminal / verified shift end** | D3 prevails over earlier 30 days. Purge on complete/cancel; restore/backups addressed separately |
| Delivery customer contact and address operational copy | **90 days** | last associated terminal order/case closure, no other valid purpose or legal hold |
| CS notes and customer notification content | **90 days** | resolved case / last related terminal order |
| Nonfinancial operational order/route/trip details | **365 days** | delivered/cancelled terminal closure (not `FAILED` while awaiting replan) |
| Former staff nonstatutory account/contact | **90 days** | employment ended, no active assignment/legal hold; disable access immediately |
| Nonstatutory warehouse staff shifts/attendance | **24 calendar months** | end of duty period, subject to national rules/collective agreements |
| Technical error/application logs | **30 days** | event timestamp, redact PII |
| Access/security logs | **90 days** | event timestamp, privacy minimization |
| Staging backup snapshots | **max 30 days** | snapshot time; provider-specific controls must be confirmed |
| Regulated tachograph records | **at least 12 calendar months** | when Regulation (EU) 165/2014 applies; NOT raw live GPS |
| Regulated driver working-time records | **at least 24 calendar months** | where applicable under Directive 2002/15/EC / Swedish implementation |
| Qualifying Swedish accounting materials | **through Dec 31 of 7th calendar year after the year fiscal year ended** | only where records truly are accounting information; calculate from financial-year end |
| Audit/milestone immutable records | **24-month REVIEW WINDOW ONLY; no unconditional deletion** | verify lawful basis/claims/statutory categories and no PII; do not UPDATE/DELETE immutable audit |
| DSAR request | **normally 1 calendar month** | may be extended in qualifying cases, GDPR Art 12(3) |
| Reportable GDPR personal-data breach | **within 72h** | controller awareness, when notification threshold met, Art 33 |

**Legal guardrail:** this is a concrete **product retention configuration**, not legal certification of Swedish/GDPR compliance. The data controller and legal/privacy reviewer must verify actual lawful basis, purposes, national tax/labour obligations, legal holds, ROPA, privacy notices, access controls, backup erasure, DPA and international transfers **before real personal data go live**. For a purpose that ends sooner than an approved maximum, delete earlier; where law genuinely requires longer, separate the statutory archive from ordinary operations with restricted access. Never automatically purge regulated records after an arbitrary shorter period, and never claim anonymous when only pseudonymous.

**Implementation:** versioned `retention_policy` register with type/purpose/lawful basis/retention rule/unit/anchor/legal exceptions, legal-hold handling and dry-run counts; cutoff by business date/time and fiscal year accurately; delete/obscure only applicable personal fields without breaking FK or immutable audit. Do not make `data_retention_days.personal=365` / `order=730` appear as proof of compliance. Deletion must handle DB, caches, device offline queue and backup propagation. Legal reviewer signs off before enabling real-data deletion.

Sources: https://www.imy.se/en/frequently-asked-questions/how-long-can-we-keep-personal-data/ ; https://www.riksdagen.se/sv/dokument-och-lagar/dokument/svensk-forfattningssamling/bokforingslag-19991078_sfs-1999-1078/ ; https://eur-lex.europa.eu/eli/reg/2014/165/oj/eng ; https://transport.ec.europa.eu/transport-modes/road/social-provisions/working-time_en .
