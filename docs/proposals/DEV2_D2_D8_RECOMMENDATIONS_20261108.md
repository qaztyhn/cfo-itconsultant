## D2 — CSV fallback

- Only IT/admin can upload the source CSV fallback; API remains primary, CFO never writes into POS. Version each schema (`schema_version=1` via uploaded manifest). Package related data as `orders.csv` + `order_lines.csv` sharing `order_id` and a manifest containing `market`, `entity`, `captured_at`, and `sha256`. Other allowed entity files: customers, addresses, products, inbound and fleet; stock requires a **complete snapshot manifest/batch** per Q9, not unsafe row-based aggregation.
- UTF-8 (BOM tolerated), RFC 4180 quoting, header fixed per reviewed Source API DTO, comma delimiter, ISO 8601 date, offset-aware timestamps, 24h time, decimal point, no localized thousands separators, money as exact 2-digit decimal string. Unknown/missing required headers or unknown market/schema => reject without partial state update. Limit upload size (proposal 20 MiB), validate content/hash before transaction.
- Compute SHA-256 of the original uploaded bytes, scoped by (market, entity, schema_version). Previous `ok` => `SKIPPED_SAME_HASH`; previous `failed` => new auditable retry sync_run, never hide failure; previous `partial` => manual IT review then retry (never auto-skip); concurrent `running` => `409 SYNC_IN_PROGRESS`. Current unique index admits `partial`, so review migration before implementing retry; retain full run history.
- Idempotent upsert by entity natural key and source version, reject same-key conflicting rows, log per-row rejects without PII in technical logs, never sum duplicate stock rows; checkpoint and stock-batch publish only after coherent validation.

## D3 — GPS endpoints, permissions and bounded DTOs

- **Already fixed:** driver can upload only own trip; dispatcher alone can read live/history; `gps_enabled=false` rejects upload and reads; upload requires actual `on_road` trip; no GPS in other user roles/notifications or generic log fields. Do not loosen existing rules.
- Proposed `POST /trips/{id}/positions`: `{positions:[{lat,lon,accuracy_m?,recorded_at,source:"device"|"simulator"}]}`, 1..100 points per batch; finite lat [-90,90], lon [-180,180], accuracy positive and <= 10,000 m if present; offset-aware timestamps <= server now + 5 min and not earlier than trip dispatch (allow limited offline queue while trip is on-road). All-or-nothing payload validation; `200 {trip_id,accepted,duplicates,latest_recorded_at}`. Duplicate points of same trip+time+source do not create new points; contradictory duplicate values are rejected, not silently overwritten. Invalid -> 422, disabled -> 403 GPS_DISABLED, wrong ownership -> 404/403 per scope policy, not-on-road -> 409 NOT_ON_TRIP.
- `GET /trips/{id}/positions?since=...`: dispatcher market-scoped, ascending timestamp + id, pagination default 50/max 500, bounded date window (proposed maximum 7 days per call), never beyond configured retention. `GET /gps/live`: dispatcher-only, active trips within authorized market; `{items:[{trip_id,vehicle_id,recorded_at,lat,lon,accuracy_m,source,eta,risk_color,gps_status}],as_of}`. `gps_status` distinguishes `fresh|lost|no_fix` by market `lost_min`, no fabricated zero coordinates.
- `GET/PUT /markets/{code}/gps-settings`: admin only, `{gps_enabled,interval_min,lost_min,retention_days,warnings[]}`; proposed validated bounds interval 1–60 min, lost >= interval and <= 240 min, retention 1–30 days. Defaults remain currently approved 30/60/30; config changed only with audit. Demo can enable with `DPIA_MISSING` warning/banner as current contract, but **no real-driver GPS before privacy/compliance review**. Simulator source must remain marked `simulator`.

## D4 — notifications

- Automatic templates stay `CONFIRMED,DISPATCHED,DELIVERED,FAILED`; `DELAY` is created as draft and only Dispatcher may send/discard. Message variables allowed: public order code, delivery status, approved promised window or revised ETA window, approved standard customer-service footer. No GPS coordinates, driver/employee names, private internal risk scores, warehouse operational details or unrestricted personal prose.
- Resolve 03/06 vs 09 conflict in favor of **controlled editing**. For MVP "Edit DELAY" allows changing `eta_window` and selecting a reviewed standard phrase / reason code, not arbitrary body text. Server must render final subject/body from allowlisted tokens. `body` supplied to existing send endpoint must either match server-rendered preview exactly or be rejected 422; update 03/06 to remove suggestion of arbitrary free-text outbound. `POST /orders/{id}/delay-notice` creates an auditable draft rather than bypassing the dispatcher approval gate.
- Recipient masking; required idempotency on send, dedupe per order + template + plan/trip + ETA version. Quiet hours 21:00–07:00 by market except manual DELAY per existing rule. Max 3 attempts including first; proposed backoff 5 min then 15 min (market configurable), stop after third and alert IT. Unknown SMTP-delivery outcome must not be asserted exactly-once: stay test-only/Mailpit/external recipient allowlist per DEC-NOTIFY-001, no customer production mail until reconciliation exists. Suppressed is not retried.

## D5 — retention and anonymization

- Preserve market-configurable demo defaults: GPS `30` days from *trip terminal completion/cancellation time*; order records `730` days from terminal `DELIVERED/CANCELLED` closure (FAILED with pending replan is NOT terminal); personal data `365` days after the **last relevant terminal order or end of employment**, considering all live relations and legal hold. Define separate employee statutory retention later for real deployment; never assume these defaults prove GDPR compliance.
- GPS records from still-open trips are not silently deleted on missing finish timestamp; overdue open trips create an operational cleanup alert. Never collect positions outside active trip. Customer/employee shared records cannot be anonymized while referenced by an active order, shift, assignment, dispute or preservation obligation. Use durable surrogate identifiers and detach/remove unnecessary contact fields without destroying FK/history.
- Immutable `audit.decision_log` and `ops.milestone_event` must NOT be updated/deleted to anonymize PII. Prevent raw names, emails, phones, addresses, coordinates and free-text PII from being written to immutable snapshots at creation. If legacy logs already contain PII, flag privacy remediation/legal review, do not claim they were anonymized. Audit retention run itself, dry-run preview/counts, legal-hold skip, staged idempotent reruns.
- Before using real personal data, review actual national statutory retention / GDPR storage limitation and DPIA/employee notices. Prefer demo synthetic-only until confirmed.

## D7 — synthetic vehicle and driver legality fixtures

- No deriving `max_permissible_mass_kg` or `regulation_561_scope` from payload capacity. Provide explicit **synthetic manufacturer-style attributes**, including mass of vehicle+trailer, cargo capacity, transport mode `domestic|international|cabotage`, exemption notes/evidence, `in_scope|out_of_scope|unknown` classification, source marker `synthetic_demo`. Unknown => fail-closed for driver feasibility.
- For Sweden domestic demo, explicitly scoped heavy trucks (e.g. permissible mass 12,000/18,000/26,000 kg) can have `in_scope` where there are no exceptions; a van with exactly 3,500 kg permitted mass and no trailer may be `out_of_scope` in domestic transport if qualified. **From 2026-07-01, goods LCV >2,500 kg in qualifying international transport/cabotage must be scope-reviewed**, so never use "van" as a blanket exclusion. The EEA/individual-national exceptions still require compliance review.
- Seed 56 days of explicit synthetic duty/driving/rest history per driver (plus planned future shifts), including time zone, trip intervals, duty vs actual driving, 11-hour daily-rest policy, driving breaks and weekly/two-week cases as applicable. Include golden fixtures: feasible, <11h daily rest, insufficient weekly history, driving-limit breach, unclassified/unknown scope, trailer-induced scope change. No auto-assignment to warehouse or driver shifts; Warehouse Manager must confirm named roster and the actual driver's schedule. Do not label synthetic fixture as legal compliance certification.

## D8 — secured scheduler and internal tick

- `POST /internal/tick?job=<name>&market=<code?>` requires `X-Internal-Key` and configured source/market scope; return completed response `{job,market,status:"ok",started_at,finished_at,processed,failed}` where supported. Unknown/unimplemented job => 404/422 controlled response, never invoke stubs that raise NotImplementedError. In-flight same job/scope => 409 `SYNC_IN_PROGRESS` (or documented JOB_ALREADY_RUNNING if approved).
- Proposed whitelist **when implemented and tested only**: market-scoped `ingest_orders`, `refresh_stock`, `morning_check`, `nightly_metrics`; global `hold_expiry`, `notify_outbox`, `gps_lost`, `retention`. Check actual function/module readiness before adding to whitelist. Some jobs exist now only as stubs, so enable gradually.
- Default cadence: ingest and stock 5 minutes per market; hold expiry and outbox every 1 minute; GPS loss every 5 minutes; morning check market-local 07:00; nightly metrics and retention off-peak market-local daily. Business times use each market IANA timezone incl DST, never UTC-midnight approximations. Each job idempotent, DB advisory lock by (job,market) across app instances and external cron; no overlapping APScheduler + external cron without a single leader. Timeouts/failed items must return safe status, not fabricate processed counts. Sensitive job payloads and secrets never logged.
- Technical test cases: wrong key, unknown job, missing/invalid market, concurrent tick, failed dependency, retry, DST boundary, test-market isolation, idempotency and no duplicate external notifications.
