## D1-A — Paginated source read endpoint inventory

- Page envelope for \`GET /orders\`, \`/customers\`, \`/products\`, \`/inbound\`, \`/fleet/calendar\`, \`/addresses\`: \`{items,page,page_size,total}\`, header \`X-Total-Count\`. Defaults page=1/page_size=50, max 500, invalid filters -> 422. Source list pagination is separate from CFO pagination.
- Inclusive \`updated_since\` with aware timestamp and ascending deterministic sort by \`(updated_at, natural key)\`. Natural keys: orders/customers/addresses \`id\`, products \`sku\`, inbound \`(inbound_ref,warehouse_code,sku)\`, fleet calendar \`(vehicle_code,from_ts,to_ts)\`. All list endpoints accept \`updated_since\`, including fleet calendar in addition to its time-range filter.
- \`GET /orders\`: default \`status=SUBMITTED_FOR_PLANNING\`, explicit \`status=CANCELLED\` supported. CFO must poll/ingest cancellations as well as submitted rows. \`GET /addresses\`: optional \`q\` and \`customer_id\`. Fleet \`from/to\` are aware instants and filter overlapping half-open intervals.
- \`GET /stock\` is NOT paginated: retain existing \`{as_of,items}\` snapshot contract; require future coherent batch support.
- Reader maintains durable per-feed checkpoint only after all pages complete; process overlap and replays idempotently, with tests for equal timestamp, page boundary and partially failed syncs. Do not claim offset paging alone is a transactionally frozen snapshot under concurrent writes.

## D1-B — Source POS write DTO and validation

- \`POST /orders\` creates server-generated opaque \`id\`, \`status=DRAFT\`, \`version=1\`, aware \`updated_at\`, response 201. Request may contain \`customer_id\`, \`address_id\`, \`store_code\`, \`sales_code\`, \`contact{name,phone,email}\`, \`date_mode\`, \`date_from\`, \`date_to\`, \`window_start\`, \`window_end\`, \`receiving_restrictions\`, \`special_requirements\`, \`lines[{line_no,sku,qty,unit_price}]\`. Reject extra fields; server owns address/coordinates, status, id/version/timestamps.
- Persisted draft requires \`customer_id\`, \`address_id\`, \`store_code\`, \`date_mode\` (\`exact|range|latest\`). Other content can be incomplete in DRAFT, including empty lines. A completely incomplete POS form stays local until the references are selected; do not weaken existing non-null customer/address refs.
- Server snapshots address, lat, lon from the selected customer address; verify ownership. Do NOT overwrite an old order's address snapshot merely because the mutable address record changed. On an explicit order address change or user-requested refresh, take a new snapshot and version bump; never trust client-supplied coordinates. Contact and optional text fields are snapshotted onto the order.
- For successful validation: active customer, customer-owned address, valid coordinates, sales/store references, contact name and at least phone or email; at least one source-known SKU with unique positive line_no and strictly positive finite \`qty\` (up to 3 decimal places); \`unit_price\` is a nonnegative decimal string with exactly 2 decimal places (**0 is allowed**); no unknown fields.
- \`date_mode=exact\`: \`date_from\` required and \`date_to=null\`; \`range\`: both dates and \`from<=to\`; \`latest\`: \`date_to\` required and \`date_from=null\`. Local business dates and receiving hours use source-instance IANA timezone and explicit address calendar. \`window_start/window_end\` are either both absent or both \`HH:MM\`, with start < end; require overlap/containment in address receiving schedule as specified by contract. Unknown calendar => fail closed; no guessed 24/7.
- \`special_requirements\` / \`receiving_restrictions\` remain optional text in the current MVP DTO; text is **not** a trusted automatic vehicle/handling capability. If an operational safety condition cannot be represented by existing structured planning fields, require Dispatcher review; do not auto-approve a Sales plan based on guessed text.
- Framework and business validation failures: \`422 VALIDATION_ERROR\` and \`details.errors[{loc,type,msg}]\`, stable machine-readable \`type\`, no echoed input values or PII. Suggested source business types: \`customer_not_found\`, \`address_customer_mismatch\`, \`missing_coordinates\`, \`contact_required\`, \`invalid_date_mode\`, \`invalid_date_range\`, \`invalid_receiving_window\`, \`outside_receiving_hours\`, \`receiving_calendar_missing\`, \`lines_required\`, \`duplicate_line_no\`, \`unknown_sku\`, \`invalid_quantity\`, \`invalid_price\`. Framework types remain stable as documented. An unmapped-but-existing source SKU MUST NOT be rejected by POS validation: it belongs to ASM-005 CFO/legacy routing.
- \`POST\` returns 201 with same order representation as existing GET. PUT/validate/submit/cancel return 200; money strings, numeric quantities, aware timestamps, lines ordered by line_no. Source OpenAPI must be generated/reviewed. Do not expose actual address/contact values in errors or technical logs.

## D1-C — Lifecycle and cancellation propagation

- \`PUT /orders/{id}\` is full replacement of editable fields and lines in one transaction, with required \`expected_version\`; server compares under row lock and increments version on a material change. Stale version -> 409 \`VERSION_CONFLICT\` (**proposed source-only code requiring 06 update**); nonpermitted state -> 409 \`ILLEGAL_TRANSITION\`. A true identical no-op may return current version without a new event.
- \`DRAFT -> VALIDATED -> SUBMITTED_FOR_PLANNING\`: validate/revalidate under lock with no version/status change on failure; validate on DRAFT bumps once; repeated successful validate/submit are idempotent if no changes; submission locks row and bumps version once. Editing VALIDATED returns it to DRAFT, invalidating the prior validation.
- \`PUT\` on an already \`SUBMITTED_FOR_PLANNING\` order is permitted **only with a fully valid replacement** and expected_version under one transaction; the source order remains \`SUBMITTED_FOR_PLANNING\`, version/updated_at increase, and CFO sees a new source version. Invalid PUT is rejected atomically and does not silently remove the order from the submitted feed. \`CANCELLED\` cannot be edited/reopened.
- \`POST /orders/{id}/cancel\` supports DRAFT/VALIDATED/SUBMITTED_FOR_PLANNING; require version and a cancel reason (structured reason_code and optional safe text, mandatory when \`other\`). It sets \`CANCELLED\`, increments version once, keeps immutable cancellation provenance, and returns 200 same DTO. Repeated cancellation is idempotent; terminal \`CANCELLED\` cannot be edited or submitted again.
- CFO adapter must fetch \`CANCELLED\` changes with inclusive updated_since / independent checkpoint, compare \`source_version\` and handle according to order routing/state. Already-routed legacy orders never silently become CFO. CFO must not write back to POS. For CFO pre-approval: close/release holds and transition to cancelled only via **explicitly reviewed allowed transitions, audit and transaction** (e.g. current SUBMITTED -> CANCELLED must not be invented in existing transition table). After CFO approval or when any dispatch/execution has begun: no blind overwrite/cancellation; raise high-priority source-change/cancel alert, block unsafe new progression where possible, and have Dispatcher decide. Dispatched/delivered history is never silently erased. Source edit after CFO approval similarly triggers ORDER_CHANGED_AFTER_APPROVAL / suggested replan, not automatic confirmation.
- Add regression tests: duplicate POST safety, stale edit, concurrent cancel vs PUT, valid edited submitted order, cancelled feed across pagination, read-only CFO source boundary, approved/ongoing order protected against source changes, no duplicate fulfilment. Reconcile API/idempotency error codes in 05/06/09 before implementation.

## D1-D — Remaining SRC-Q8/9/10 implementation defaults to review

- Q8 calendar: per-instance market timezone, explicitly seeded working/holiday calendar and receiving slots per address. No global always-open fallback, no fabricated holidays. Missing data prevents submission validation; warehouse/driver schedules remain CFO-only separate gates.
- Q9 stock: use a transactionally published **full snapshot batch** with one authoritative \`as_of\` and uniquely keyed rows, including a published zero-row batch. No published batch/failed load => unavailable (never silently zero stock). Empty **published** complete batch may mean authoritative zero only under explicit completeness marking and safe CFO replacement. The merged interim \`min(per-row as_of)\` is not Q9 compliance.
- Q10 normalization: introduce explicit physical stock-pool identity per warehouse so multiple local aliases for one physical inventory count **once**, distinct pools can sum after conversion to global base units via \`units_to_base\`. Reject/quarantine ambiguous pool identity and inconsistent converted quantities, avoid last-row-wins and blind summation; test same pool aliases vs separate pools, units conversion and missing mappings. Dev 1 + Dev 2 must agree the migration and adapter DTO before production of stock persistence.
